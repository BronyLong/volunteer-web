# ВВЕДЕНИЕ

В современных условиях всё более значимой становится задача эффективной организации волонтёрской деятельности. С ростом количества проводимых мероприятий и увеличение количества участников усложняется проведение процессов взаимодействия. В данной ситуации появляется необходимость применения специализированных информационных систем.

Привычные способы проведения волонтёрской работы, заключающиеся в использовании таблиц и социальных сетей, обладают ограниченной эффективностью. Их применение усложняет планирование мероприятий, повышает нагрузку на организаторов, затрудняет обработку заявок и увеличивает вероятность возникновения ошибок при работе с данными. Кроме того, такие способы могут обеспечить удобство для пользователей, поскольку информация распределяется между разными средствами получения и обмена информацией.

В ходе работы осуществлялась разработка веб-приложения для волонтёрской организации. Его предназначение состоит в управлении мероприятиями, регистрации пользователей и обработке заявок на участие. При разработке основной акцент был сделан на удобстве использования приложения: интерфейс должен быть понятным для пользователей, взаимодействие с платформой не должно ограничиваться веб-браузерами, доступными с персональных компьютеров, а основные действия выполняться без большого количества переходов между страницами.

Разрабатываемое приложение построено на основе клиент-серверной архитектуре. В его состав входят клиентская часть, серверная логика и база данных. Для разграничения прав доступа в системе предусмотрены роли пользователей, каждой из которых предоставлен собственный набор возможностей.

В процессе выполнения работы были проведены анализ предметной области, проектирование структуры системы, разработка пользовательского интерфейса и реализация программной логики приложения. Дополнительно были проработаны механизмы взаимодействия клиентской и серверной частей, организация хранения данных, обработка пользовательских заявок, контроль доступа к функциональным возможностям и удобство выполнения основных пользовательских сценариев.

Результатом выполненной работы стало веб-приложение, позволяющее автоматизировать основные процессы волонтёрской деятельности и повысить удобство взаимодействия между пользователями системы.

# Анализ предметной области

Волонтёрская деятельность представляет собой добровольное и безвозмездное выполнение работ либо оказание услуг, направленных на достижение общественно значимых целей. К основным направлениям такой деятельности относятся социальная поддержка граждан, помощь людям, находящимся в трудной жизненной ситуации, участие в ликвидации последствий чрезвычайных ситуаций, охрана окружающей среды, развитие образования, культуры, здравоохранения и спорта. Кроме того, волонтёрство охватывает патриотическое воспитание, благотворительные и молодёжные инициативы, содействие поиску пропавших людей, развитие донорства, оказание правовой и медицинской помощи, поддержку семьи и сохранение исторической памяти [1].

В современных условиях наблюдается рост развития волонтёрского движения: количество добровольцев увеличивается, расширяется перечень направлений помощи, а также рост числа проводимых мероприятий. Данные формируют потребность в более эффективных средствах организации деятельности. Согласно данным платформы «Добро.ру», в России зарегистрированы миллионы волонтёров, участвующих в различных проектах, что подтверждает значимость цифровых инструментов для координации участников и мероприятий [2].

Одной из наиболее значимых задач в данной предметной области является организация взаимодействия между волонтёрами и координаторами. При большом количестве участников требуется своевременно учитывать заявки и контролировать доступность мест.

Распространённой проблемой также остаётся использование разрозненных инструментов, таких как электронные таблицы или социальные сети. Такой подход затрудняет поиск актуальных данных, увеличивает вероятность ошибок при обработке заявок и снижает общую эффективность управления мероприятиями.

Дополнительное значение имеет удобство взаимодействия пользователей с системой. Волонтёрам необходимо быстро находить подходящие мероприятия, подавать заявки и получать уведомления об изменении их статуса с любых устройств. Координаторам, в свою очередь, требуется понятный инструмент для создания мероприятий и рассмотрения и подтверждения заявок, а также подтверждения фактического участия после завершения события.

Отдельно следует выделить проблему прозрачности процессов. При отсутствии централизованного учёта становится сложнее выполнять все выше названные задачи. Это негативно влияет на качество организации волонтёрской деятельности и затрудняет последующий анализ выполненной работы.

Таким образом, анализ предметной области показал необходимость разработки веб-приложения, обеспечивающего централизованное управление волонтёрской деятельностью. Такая система должна автоматизировать процессы необходимые для работы волонтерской организации. Наряду с этим она должна обеспечивать удобное взаимодействие пользователей, их своевременное информирование и контроль фактического участия.

# Цели и назначение разрабатываемого продукта

Разрабатываемый программный продукт представляет собой веб-приложение, предназначенное для автоматизации деятельности волонтёрской организации и упрощения взаимодействия между участниками системы.

Система обеспечивает хранение информации о пользователях, профилях, мероприятиях и заявках в единой базе данных. За счёт этого снижается зависимость организации от разрозненных средств коммуникации, а основные действия пользователей выполняются в рамках одного веб-интерфейса. Волонтёры получают возможность просматривать мероприятия и подавать заявки на участие, координаторы - создавать мероприятия и обрабатывать заявки, администраторы - контролировать работу приложения в целом.

Программный продукт ориентирован на следующие категории пользователей:

− волонтёры - пользователи, подающие заявки и принимающие участие в мероприятиях;

− координаторы - пользователи, создающие мероприятия, редактирующие информацию о них, а также управляющие заявками участников;

− администраторы - пользователи, осуществляющие контроль за работой системы, пользователями, мероприятиями и журналом действий;

− потенциальные волонтёры (гости) - посетители сайта, знакомящиеся с деятельностью организации и доступными мероприятиями.

Основной целью разработки является создание удобной и простой в использовании платформы для организации волонтёрской деятельности. При проектировании приложения учитывалась необходимость сделать основные пользовательские сценарии понятными: взаимодействие с платформой должно выполняться без лишних действий и сложной навигации.

К основным целям разработки относятся:

− упрощение регистрации и взаимодействия пользователей;

− оптимизация процесса организации мероприятий путём предоставления координаторам инструментов создания, редактирования и сопровождения событий;

− обеспечение удобного доступа к информации о мероприятиях с большинства устройств и по понятной логике;

− централизация данных о пользователях, мероприятиях, заявках, уведомлениях и действиях пользователей в единой информационной системе.

На практике деятельность волонтёрских организаций часто сопровождается использованием множества независимых друг от друга инструментов.

В результате возникают следующие проблемы:

− отсутствие централизованного хранения данных;

− усложнение процесса организации мероприятий;

− неудобство записи участников и обработки заявок;

− высокая вероятность потери, дублирования или несвоевременного обновления информации.

Разработка специализированного веб-приложения позволяет решить указанные проблемы за счёт объединения основных процессов в одной системе.

Таким образом, создание веб-приложения, объединяющего все процессы работы волонтерской организации воедино, является обоснованным и целесообразным решением.

# Архитектура
## Общая архитектура системы

Проектирование архитектуры веб-приложения включает определение основных компонентов системы, распределение ответственности между ними и описание способов их взаимодействия. Для разрабатываемого веб-приложения архитектура построена по многослойному принципу и ориентирована на поддержку ключевых процессов.

Общая схема приложения включает клиентскую часть, серверную часть, базу данных, веб-сервер и инструменты сопровождения. Пользователь взаимодействует с системой через браузер или мобильное устройство. Доступ к приложению осуществляется по доменному имени с использованием защищённого HTTPS-соединения, что обеспечивает передачу данных между пользователем и сервером по протоколу TLS [6].

В качестве входной точки используется Nginx. Он выполняет функции обратного прокси, маршрутизирует входящие запросы и разделяет обработку статических файлов frontend-части и API-запросов к серверной части [7]. 

Клиентская часть приложения реализована с помощью декларативной библиотеки React и сборщика веб-проектов Vite. В клиентской части используются React Router для маршрутизации внутри одностраничного приложения, JavaScript для реализации логики интерфейса, CSS и методология БЭМ для организации стилей. 

Клиентский слой отвечает за отображение страниц, обработку действий пользователя, хранение состояния интерфейса и отправку запросов к серверному API.

Серверная часть реализована с помощью платформы Node.js и фреймворка Express. Backend API принимает HTTP-запросы от клиентского приложения, выполняет проверку входных данных, проверяет JWT-токены и применяет ролевую модель доступа. Для защиты паролей используется bcrypt, а доступ к возможностям системы ограничивается в в зависимости от пользователя. 

Взаимодействие клиента и сервера выполняется через API-запросы, в которых данные передаются в формате JSON, а авторизация защищённых операций осуществляется с применением JWT.

Для запуска и мониторинга серверного процесса используется PM2. Он позволяет поддерживать backend-приложение в рабочем состоянии, отслеживать его выполнение и перезапускать процесс при сбоях [8]. Это особенно важно при развёртывании приложения в серверной среде, поскольку backend должен работать постоянно и быть доступным для обработки запросов пользователей.

Слой хранения данных реализован на PostgreSQL. База данных используется для хранения информации, требуемой для работы системы.

Таким образом, архитектура приложения включает несколько взаимосвязанных компонентов: пользовательский браузер, защищённый доступ по доменному имени, Nginx, frontend-часть, backend API, PM2 и PostgreSQL. Такое разделение позволяет изолировать пользовательский интерфейс, серверную бизнес-логику и хранение данных, а также упростить сопровождение и дальнейшее развитие системы.

## Основные слои приложения

Архитектура веб-приложения может быть представлена в виде следующих уровней.

Клиентский слой отвечает за пользовательский интерфейс и взаимодействие пользователя с системой на React. На данном уровне находятся основные страницы для взаимодействия с приложением.

Серверный слой представлен Backend API на Node.js и Express. На этом уровне реализованы основные правила предметной области.

Слой хранения данных представлен PostgreSQL. В базе данных размещаются основные сущности приложения. Использование реляционной базы данных позволяет формализовать связи между сущностями, применять ограничения целостности и выполнять выборки, необходимые для отображения данных в интерфейсе.

Инфраструктурный слой включает Nginx, HTTPS и PM2. Nginx принимает внешние запросы, отдаёт статические файлы frontend-части и перенаправляет API-запросы на backend. HTTPS обеспечивает защищённую передачу данных между пользователем и сервером. PM2 используется для запуска и мониторинга серверного процесса.

Отдельно выделен слой тестирования. Он не участвует напрямую в обработке пользовательских запросов, но используется при разработке и сопровождении системы. Для тестирования frontend-части применяются Vitest и Testing Library, для проверки backend API используются Vitest и Supertest, а анализ покрытия выполняется с использованием Coverage V8.

## Взаимодействие компонентов

Взаимодействие компонентов системы начинается с обращения пользователя к веб-приложению. Пользователь открывает сайт, запрос поступает на Nginx, который определяет дальнейший путь обработки.

При запросе страниц приложения Nginx отдаёт статические файлы frontend-части. После загрузки React-приложение управляет отображением интерфейса. Переходы между разделами выполняются на стороне клиента, что позволяет избежать полной перезагрузки страницы и повысить удобство работы.

При выполнении действий, требующих обращения к серверу, frontend отправляет API-запросы к backend. Данные передаются в формате JSON. Для защищённых операций к запросу добавляется JWT-токен.

Nginx перенаправляет API-запросы на серверную часть приложения. Backend API на Express принимает запрос и обрабатывает его. После этого сервер обращается к PostgreSQL через библиотеку pg, выполняет необходимые SQL-операции и получает результат.

Ответ сервера возвращается клиентскому приложению в формате JSON. После получения ответа React обновляет состояние интерфейса: отображает данные профиля, список мероприятий, статус заявки, уведомления, ошибки формы или результат выполненного действия. Такой механизм обеспечивает согласованную работу frontend, backend и базы данных.

Для серверного процесса используется PM2. Он запускает backend API, отслеживает состояние процесса и обеспечивает его постоянную работу. Благодаря этому backend остаётся доступным для обработки запросов даже после завершения терминальной сессии или при необходимости автоматического перезапуска.

## Управление волонтёрскими мероприятиями

Процесс управления волонтёрскими мероприятиями включает такие процессы как:
- создание, редактирование и удаление мероприятий; 
- просмотр поданных заявок, а также их подтверждение или отклонение;
- контроль участия волонтеров в мероприятиях;
- уведомление волонтеров о появлении новых или срочных мероприятий.
 
 Основным участником данного процесса является координатор, который отвечает за подготовку и сопровождение мероприятий.

Процесс начинается с входа координатора в систему. После авторизации пользователь переходит в раздел управления мероприятиями. На данном этапе проверяется роль пользователя. Доступ предоставляется пользователям с ролью координатора. При отсутствии необходимых прав система блокирует дальнейшее выполнение операции.

После успешной проверки координатор выбирает необходимое действие: создание, редактирование или удаление мероприятия. При создании мероприятия координатор заполняет параметры, необходимые для описания конкретного события. Система проверяет корректность введённых данных. При обнаружении ошибок отображается соответствующее сообщение, а операция не выполняется. Если ошибки отсутствуют, мероприятие сохраняется в системе и становится доступным для просмотра пользователями.

При редактировании координатор изменяет данные уже созданного мероприятия. Система также выполняет проверку корректности обновлённых сведений. В случае успешной проверки данные мероприятия обновляются, после чего изменения отображаются на странице мероприятия и в общем списке доступных событий. При наличии ошибок система сообщает о них координатору и не сохраняет некорректные данные.

Удаление мероприятия выполняется после выбора соответствующего действия и подтверждения операции координатором. После подтверждения система удаляет мероприятие из базы данных, и оно перестаёт отображаться пользователям в списке мероприятий. Дополнительная стадия подтверждения необходима для предотвращения случайного удаления данных.

Отдельным действием в рамках процесса является просмотр заявок на мероприятие. Координатор открывает страницу мероприятия, в которой находится список поданных заявок, и получает сведения о пользователях, выразивших желание принять участие.

Результатом процесса является актуальное состояние данных о волонтёрских мероприятиях в системе. В процессе выполнения операции мероприятие может быть создано, изменено, удалено или открыто для просмотра вместе со списком заявок. При нарушении прав доступа или вводе некорректных данных операция завершается без изменения информации в системе.

## Диаграмма BPMN

Диаграмма BPMN отражает процесс подачи заявки волонтёром на участие в мероприятии, а также последующую обработку данной заявки веб-приложением и координатором. В процессе участвуют три стороны: волонтёр, веб-приложение и координатор. Такое разделение позволяет показать, какие действия выполняются пользователем, какие проверки осуществляются системой и в каких случаях координатор вмешивается в обработку заявки.

Процесс начинается с того, что волонтёр открывает страницу выбранного мероприятия и нажимает кнопку «Подать заявку». После выполнения данного действия веб-приложение проверяет, авторизован ли пользователь в системе. При невыполнении данного условия пользователь перенаправляется на страницу входа, а процесс подачи заявки завершается без создания новой записи.

При успешной проверке авторизации система переходит к проверке существующих заявок пользователя на выбранное мероприятие. Данный этап необходим предотвращает повторную подачу заявки одним и тем же волонтёром. Если существующая заявка обнаружена, веб-приложение выводит соответствующее сообщение, после чего процесс завершается.

При отсутствии ранее созданной заявки система проверяет наличие свободных мест на мероприятии. Такая проверка не допускает превышения установленного лимита участников. Когда свободные места отсутствуют, пользователю отображается соответствующее сообщение, а заявка не создаётся.

При наличии свободных мест веб-приложение создаёт заявку на участие в мероприятии, уменьшает количество доступных мест и отображает пользователю статус заявки. После этого волонтёр может просматривать состояние своей заявки на странице мероприятия. При необходимости пользователь имеет возможность отозвать заявку до участия в мероприятии.

Отдельная часть диаграммы описывает действия координатора. Координатор просматривает список заявок, поданных на мероприятие, и оценивает необходимость отклонения конкретной заявки. Если отклонение не требуется, дальнейшие действия со стороны координатора не выполняются.

Если необходимость отклонения присутствует, например, если волонтер не сможет участвовать в мероприятии ввиду объективных причин, координатор нажимает соответствующую кнопку. После этого веб-приложение изменяет статус заявки на отклонённый, увеличивает количество доступных мест и обновляет статус заявки. Волонтёр при просмотре страницы мероприятия видит состояние своей заявки.

Таким образом, диаграмма демонстрирует последовательную обработку заявки на участие в мероприятии.

## Диаграмма EPC

Диаграмма EPC отражает процесс создания волонтёрского мероприятия координатором. Она описывает последовательность действий пользователя и системы от открытия формы до публикации события для волонтёров.

Начальным событием является авторизация координатора. После входа пользователь открывает страницу создания мероприятия, а система отображает форму ввода данных. В неё вносятся данные, необходимые для описания мероприятия.

После заполнения форма передаётся на проверку. На диаграмме этот этап представлен через логический оператор XOR, поскольку результатом проверки может быть либо обнаружение ошибок, либо успешное создание мероприятия. При некорректных данных система выводит сообщения в форме, а координатор возвращается к исправлению введённой информации.

После успешной проверки мероприятие сохраняется в системе и становится доступным волонтёрам для просмотра и подачи заявок. Такой процесс позволяет предотвратить публикацию неполных или ошибочных сведений.

## Концептуальная модель данных

Концептуальная модель данных отражает основные объекты предметной области и связи между ними без детализации внутренней структуры сущностей. На этом уровне определяется, какие данные необходимы системе для поддержки ключевых процессов веб-приложения волонтёрской организации.

В модели выделены пользователь, профиль пользователя, мероприятие, категория мероприятия и заявка на участие. Центральной сущностью является пользователь, поскольку с ним связаны регистрация, авторизация, участие в мероприятиях и создание событий при наличии соответствующей роли.

Пользователь связан с профилем отношением «один к одному». Каждой учётной записи соответствует один профиль, содержащий дополнительные персональные сведения. Такое разделение позволяет отделить данные для входа в систему от информации, отображаемой в профиле.

Сущность «Мероприятие» связана с пользователем отношением «один ко многим»: один координатор может создать несколько мероприятий, а каждое мероприятие имеет одного пользователя-создателя. Категория также связана с мероприятиями отношением «один ко многим», поскольку одна категория может включать множество событий.

Заявка на участие связывает пользователя и мероприятие. Один пользователь может подать несколько заявок на разные события, а одно мероприятие может содержать заявки от нескольких волонтёров. Благодаря этой сущности фиксируется намерение пользователя принять участие в конкретном мероприятии.

Концептуальная модель определяет основные объекты системы и служит основой для последующего построения логической и физической моделей данных.

## Логическая модель данных

Логическая модель данных уточняет состав сущностей, их атрибуты и связи. Данный уровень описывает структуру данных подробнее, чем концептуальная модель, но ещё не привязывает её полностью к особенностям конкретной СУБД.

В модели представлены сущности User, Profile, Event, Category и Application. Каждая из них соответствует объекту предметной области и используется для хранения данных, необходимых приложению.

Сущность User содержит сведения об учётной записи: идентификатор, адрес электронной почты, пароль, роль, признак активности и дату создания. Эти данные применяются при регистрации, авторизации и разграничении доступа.

Сущность Profile хранит расширенную информацию о пользователе: имя, фамилию, телефон, город, аватар, биографию и ссылки на социальные сети. Она связана с User отношением «один к одному», так как одному пользователю соответствует один профиль.

Сущность Event описывает волонтёрское мероприятие. В её состав входят название, описание, дата и время начала, место проведения, лимит участников, количество доступных мест, категория и пользователь-создатель. Связь с User отражает роль координатора, а связь с Category позволяет классифицировать мероприятия по направлениям.

Сущность Category содержит справочную информацию о категориях. Одна категория может использоваться для нескольких мероприятий, образуя отношение «один ко многим» с Event.

Сущность Application представляет заявку пользователя на участие. Она связывает пользователя и мероприятие, а также хранит статус заявки и время её создания. Такая структура позволяет учитывать, кто подал заявку, на какое мероприятие она относится и в каком состоянии находится.

Таким образом, логическая модель показывает состав сущностей, их основные атрибуты и связи, необходимые для реализации функциональности веб-приложения.

## Физическая модель данных

Физическая модель данных показывает реализацию структуры базы данных веб-приложения в PostgreSQL. На этом уровне определяются таблицы, поля, типы данных, первичные и внешние ключи, индексы и ограничения целостности.

В модели представлены основные таблицы: users, profiles, categories, events и applications. Каждая таблица соответствует одной из сущностей логической модели и предназначена для хранения данных определённого типа.

Таблица users хранит учётные записи пользователей. В её состав входят идентификатор, адрес электронной почты, пароль, роль, признак активности и дата создания. Поле id является первичным ключом, а уникальность email предотвращает регистрацию нескольких пользователей с одинаковым адресом.

Таблица profiles содержит дополнительные сведения о пользователях: имя, фамилию, телефон, город, аватар, биографию и ссылки на социальные сети. Поле user_id одновременно является первичным ключом и внешним ключом на таблицу users, благодаря чему поддерживается связь «один к одному» между учётной записью и профилем.

Таблица categories хранит перечень категорий мероприятий. В ней содержатся идентификатор категории и её название. Уникальность названия исключает дублирование категорий.

Таблица events предназначена для хранения сведений о мероприятиях. Она включает идентификатор, название, изображение, описание, дату и время начала, длительность, место проведения, список задач, лимит участников, количество доступных мест, категорию, пользователя-создателя, дату создания и дату обновления. Поле category_id связывает мероприятие с categories, а created_by - с users.

Таблица applications хранит заявки пользователей на участие. Она содержит идентификатор заявки, идентификатор пользователя, идентификатор мероприятия, статус и дату создания. Поля user_id и event_id являются внешними ключами и связывают заявку с пользователем и мероприятием.

На физической модели отражены индексы, повышающие производительность запросов. Они используются для поиска по электронной почте, названию категории, дате начала мероприятия, категории события и заявкам. Уникальное ограничение для пары user_id и event_id предотвращает повторную подачу заявки одним пользователем на одно мероприятие.

Ограничения целостности задают допустимые значения для ключевых числовых полей. Длительность мероприятия должна быть больше нуля, лимит участников - положительным, а количество доступных мест не может быть отрицательным или превышать общий лимит. Эти правила поддерживают корректность данных на уровне базы данных.

Физическая модель показывает, каким образом сущности предметной области реализованы в PostgreSQL, и определяет структуру таблиц, ключей, связей, индексов и ограничений.

# Информационная модель системы

Информационная модель описывает потоки данных между пользователями, процессами приложения и хранилищами. Она показывает, какие сведения передаются в систему, какие процессы их обрабатывают и из каких источников приложение получает данные для выполнения пользовательских сценариев.

В рамках информационной модели отдельно рассмотрены потоки данных для гостя, волонтёра и координатора. Такое разделение позволяет отразить различия в доступных функциях и уровне взаимодействия с системой.

## Диаграмма потоков данных для гостя

Диаграмма потоков данных для гостя отражает взаимодействие неавторизованного пользователя с веб-приложением. На этом уровне доступны базовые сценарии: регистрация, авторизация и просмотр списка мероприятий.

Внешней сущностью является гость. Он передаёт в систему данные для регистрации, данные для авторизации и запрос на получение списка мероприятий. Эти действия обрабатываются процессами «Регистрация», «Авторизация» и «Просмотр мероприятий».

При регистрации гость вводит сведения, необходимые для создания учётной записи. После обработки данные сохраняются в хранилище «Пользователи», а пользователь получает подтверждение выполненного действия. Процесс авторизации проверяет учётные данные через то же хранилище и возвращает JWT-токен при успешном входе.

Просмотр мероприятий не требует авторизации. Процесс получает запрос от гостя, обращается к хранилищу «Мероприятия» и возвращает список доступных событий. При этом функции подачи заявки, управления профилем и создания мероприятий для гостя недоступны.

## Диаграмма классов

Диаграмма классов отражает объектную структуру веб-приложения. На ней представлены основные классы предметной области, их атрибуты, операции и связи.

Центральным классом является User, описывающий учётную запись пользователя. Он содержит идентификатор, адрес электронной почты, хэш пароля, роль, признак активности, дату создания и дату последнего входа. Через этот класс представлены пользователи разных ролей. Для него предусмотрены операции регистрации, входа, выхода и изменения пароля.

Для авторизации используется класс AuthService. Он отвечает за выдачу JWT-токена, проверку токена, хэширование пароля и проверку учётных данных. Такое выделение позволяет отделить логику безопасности от основных сущностей предметной области.

Класс Profile связан с User отношением «один к одному». Он хранит имя, фамилию, отчество, телефон, город, аватар, биографию и дату рождения. Разделение учётной записи и профиля позволяет отдельно хранить данные для входа и сведения, отображаемые в интерфейсе.

Класс Event описывает волонтёрское мероприятие. Он содержит идентификатор, название, краткое и полное описание, дату начала и окончания, место проведения, лимит участников и количество доступных мест. Для мероприятия предусмотрены операции создания, редактирования, удаления и получения количества свободных мест.

Класс Category используется для классификации мероприятий. Одна категория может быть связана с несколькими мероприятиями, а каждое мероприятие относится к одной категории. Такая связь обеспечивает группировку событий по направлениям деятельности.

Класс Application описывает заявку пользователя на участие. Он содержит идентификатор заявки, идентификатор пользователя, идентификатор мероприятия и дату создания. Заявка связывает пользователя и мероприятие: один пользователь может иметь несколько заявок, а одно мероприятие может содержать заявки от разных пользователей.

Сервис ApplicationService реализует логику подачи, отмены, проверки лимита, проверки повторной заявки и получения заявок по мероприятию. Сервис EventService отвечает за создание, редактирование, удаление, получение списка мероприятий и получение отдельного мероприятия по идентификатору.

Диаграмма классов показывает, что объектная структура приложения строится вокруг пользователей, профилей, мероприятий, категорий и заявок, а сервисные классы обеспечивают выполнение операций с ними.

## Диаграмма последовательности

Диаграмма последовательности описывает процесс подачи заявки волонтёром на участие в мероприятии. Она показывает взаимодействие пользователя, frontend-части, middleware, backend-логики и PostgreSQL.

Сценарий начинается с перехода пользователя на страницу мероприятия. После просмотра сведений о событии он нажимает кнопку «Подать заявку». Frontend обрабатывает действие и отправляет POST-запрос на сервер.

На серверной стороне запрос проходит через middleware. Сначала проверяются данные пользователя и его права. Для этого backend обращается к базе данных и получает сведения об учётной записи. После подтверждения корректности пользователя обработка продолжается.

Далее сервер проверяет наличие ранее созданной заявки на выбранное мероприятие. Эта проверка предотвращает повторную подачу заявки одним пользователем. При отсутствии заявки выполняется проверка свободных мест.

После подтверждения доступности участия backend создаёт новую заявку, а база данных возвращает результат операции. Затем сервер обновляет данные, необходимые для согласованного состояния мероприятия и заявок, после чего возвращает ответ клиентской части.

Frontend получает ответ и обновляет интерфейс. Пользователь видит сообщение о создании заявки или актуальный статус участия.

## Диаграмма состояний

Диаграмма состояний отражает жизненный цикл заявки волонтёра на участие в мероприятии. Она показывает основные состояния заявки и действия, приводящие к переходам между ними.

Жизненный цикл начинается с операции apply(), то есть с подачи заявки пользователем. После выполнения этого действия в системе создаётся новая запись, фиксирующая намерение пользователя принять участие в мероприятии.

После сохранения в базе данных заявка переходит в активное состояние. На этом этапе она отображается в системе и может использоваться для дальнейшей обработки. Пользователь видит состояние заявки в интерфейсе.

Операция cancel() позволяет пользователю отменить поданную заявку. После её выполнения заявка переходит в состояние «Заявка отменена», и жизненный цикл завершается.

Таким образом, диаграмма состояний показывает базовую модель жизненного цикла заявки: создание, сохранение, активное состояние и завершение через отмену.

## Диаграмма деятельности

Диаграмма деятельности описывает алгоритм подачи заявки волонтёром. Она отражает последовательность пользовательских действий и системных проверок перед созданием записи.

Процесс начинается с открытия страницы мероприятия. Волонтёр просматривает информацию и нажимает кнопку «Подать заявку». После этого система проверяет авторизацию пользователя. Неавторизованный пользователь перенаправляется на страницу входа.

Авторизованный пользователь переходит к следующей проверке: система определяет, существует ли уже заявка на это мероприятие. Обнаружение такой записи завершает сценарий отображением сообщения о повторной подаче.

Компонент Frontend отвечает за пользовательский интерфейс. Компонент Backend реализует серверную бизнес-логику. В его состав входят модули авторизации, профилей, управления мероприятиями, управления заявками и настроек профиля. Они обрабатывают запросы, проверяют права доступа и подготавливают ответы для клиентской части.

## Диаграмма развертывания

Диаграмма развертывания отражает физическое размещение компонентов и взаимодействие пользовательского устройства с серверной инфраструктурой.

### Разграничение прав доступа

В системе предусмотрены роли пользователей разработанные по модели RBAC. Каждая роль связана с определённой областью ответственности. Вместо того чтобы выдавать каждому пользователю права вручную, администратор назначает пользователям роли, а доступ к ресурсам и функциям приложения определяется уже через связанные с ними разрешения. 

Волонтёр может просматривать мероприятия, подавать заявки, отслеживать их статус, работать с профилем и уведомлениями. Координатор создаёт и редактирует собственные мероприятия, просматривает заявки и подтверждает фактическое участие после завершения события. Администратор управляет пользователями, мероприятиями и журналом аудита.

Проверка прав выполняется на сервере. Клиентская часть может скрывать недоступные элементы интерфейса, однако окончательное решение принимает backend. Такой подход защищает систему от прямых API-запросов, выполняемых без необходимых прав [11].

### Обработка заявок на участие

Логика заявок является одной из центральных частей приложения. Волонтёр подаёт заявку на мероприятие, после чего она получает статус ожидания. Координатор рассматривает заявку и принимает решение о принятии или отклонении.

В текущей реализации факт подачи заявки отделён от допуска к участию. Поданная заявка не считается подтверждённым участием автоматически, а место на мероприятии учитывается после принятия заявки координатором. Такая модель позволяет контролировать состав участников.

Дополнительно предусмотрено отклонение уже принятой заявки. Это полезно при ошибочном принятии или предварительном отказе волонтёра от участия. После изменения статуса система пересчитывает доступные места, сохраняя согласованность данных мероприятия.

### Защита персональных данных

В приложении обрабатываются сведения, относящиеся к персональным данным пользователей: адрес электронной почты, имя, фамилия, отчество, телефон, город, пол, аватар и данные профиля. При проектировании механизмов защиты учитывались требования Федерального закона от 27.07.2006 № 152-ФЗ «О персональных данных», определяющего принципы и условия обработки таких сведений [11].

При регистрации пользователь подтверждает согласие на обработку персональных данных. Создание учётной записи выполняется только после получения такого согласия, что позволяет зафиксировать волеизъявление пользователя на обработку сведений, необходимых для работы системы.

## Серверный модуль приложения

Серверный модуль реализует бизнес-логику веб-приложения и обеспечивает взаимодействие клиентской части с базой данных. Он построен на Node.js и Express. Через серверную часть выполняются регистрация и авторизация пользователей, проверка JWT-токенов, управление мероприятиями, обработка заявок, работа с профилями, уведомлениями, административной панелью и журналом аудита.

Серверная часть разделена на маршруты, middleware и вспомогательные модули. Такое разделение позволяет изолировать отдельные области логики. Например, маршруты авторизации отвечают только за регистрацию, вход и восстановление пароля, маршруты мероприятий - за работу с событиями, а административные маршруты - за управление пользователями и журналом действий.

Важной особенностью серверного модуля является проверка прав доступа на backend-уровне. Интерфейс может скрывать недоступные кнопки, однако окончательное разрешение или запрет операции выполняется сервером. Это особенно важно для действий координатора и администратора, поскольку прямой запрос к API не должен позволять пользователю выполнять операции вне своей роли.

Основные файлы серверного модуля:

- server/index.js - точка входа серверного приложения, настройка Express, middleware и API-маршрутов.
- server/db.js - подключение к базе данных PostgreSQL.
- server/middleware/auth.js - проверка JWT-токена, текущего пользователя и доступа к защищённым маршрутам.
- server/routes/.js - маршруты Backend-части приложения
- server/utils/.js - вспомогательные функции 
- server/scripts/migratePersonalData.js - служебный скрипт для шифрования данных.

Также требует особого внимания интеграция с почтовыми сервисами. Электронная почта используется для подтверждения регистрации, восстановления пароля и отправки уведомлений пользователям. Настройки почтового сервиса вынесены в переменные окружения, что позволяет изменять параметры подключения без изменения исходного кода.

# Хостинг сайта и администрирование серверной среды

Для подтверждения работоспособности веб-приложения в условиях, приближенных к реальной эксплуатации, было выполнено размещение проекта на сервере с использованием Linux-окружения. Данный этап включал не только запуск клиентской и серверной частей приложения, но и настройку операционной системы, сетевого доступа, веб-сервера, базы данных и фонового выполнения backend-процесса.

В качестве серверной машины использовалось портативная игровая консоль SteamDeck. Такой выбор обоснован предустановленной операционной системой Linux и достаточной мощностью устройства для поддержания работы веб-приложения.

Развёртывание приложения выполнялось на серверной машине, доступ к которой осуществлялся через удалённое подключение по SSH. Такой способ работы позволил выполнять администрирование операционной системы удаленно.

На сервере была подготовлена рабочая среда для выполнения приложения. Для серверной части использовались Node.js и npm, необходимые для установки зависимостей и запуска Express-приложения. Для хранения данных была настроена СУБД PostgreSQL. При работе с базой данных был создан отдельный пользователь с ограниченными правами, предназначенный для подключения приложения к базе. Такой подход позволяет не использовать системную учётную запись PostgreSQL в прикладной логике и повышает безопасность эксплуатации.

Клиентская часть приложения была подготовлена к размещению как статический frontend, а серверная часть запускалась как отдельное backend-приложение. Для обработки внешних запросов использовался Nginx. Он выполнял роль входной точки веб-приложения: принимал обращения пользователей по доменному имени, отдавал статические файлы React-приложения и перенаправлял API-запросы на серверную часть Express. Благодаря этому frontend и backend работали как единая веб-система, доступная пользователю через браузер.

Отдельное внимание было уделено настройке защищённого доступа к сайту. Для передачи данных между пользователем и сервером использовался HTTPS. Применение защищённого соединения особенно важно для данного приложения, поскольку в процессе работы передаются учётные данные, JWT-токены, сведения профиля и другая пользовательская информация. В архитектуре проекта HTTPS рассматривается как инфраструктурный механизм защиты канала передачи данных, дополняющий серверную авторизацию и обработку персональных данных.

Для постоянной работы backend-приложения был использован менеджер процессов PM2. С его помощью серверная часть запускалась в фоновом режиме, а её состояние можно было контролировать через команды управления процессами и просмотр логов. PM2 также упрощает сопровождение приложения после завершения терминальной сессии, поскольку backend продолжает работать и принимать запросы пользователей.

В ходе размещения приложения выполнялись следующие административные действия:

- настройка серверного окружения и установка необходимых зависимостей;
- подготовка PostgreSQL и прав доступа для отдельного пользователя базы данных;
- настройка Nginx для обслуживания frontend-части и проксирования API-запросов;
- запуск backend-приложения через PM2 и контроль его состояния по логам.

Таким образом, хостинг сайта потребовал выполнения работ, связанных с администрированием операционной системы и серверной инфраструктуры. Были настроены среда выполнения приложения, база данных, веб-сервер, доменный доступ, защищённая передача данных и фоновый запуск backend-процесса. В результате разработанное веб-приложение было подготовлено не только для локального запуска в среде разработки, но и для размещения в серверной среде с возможностью доступа пользователей через веб-браузер.

# План тестирования

## 1. Цели тестирования

- Проверка соответствия веб-приложения установленным функциональным и нефункциональным требованиям.
- Выявление дефектов в работе клиентской части, серверной части и взаимодействия с базой данных.
- Проверка корректности основных пользовательских сценариев для ролей: гость, волонтёр, координатор и администратор.
- Проверка корректности разграничения прав доступа между ролями пользователей.
- Оценка удобства использования пользовательского интерфейса.
- Проверка стабильности работы приложения при одновременном обращении нескольких пользователей.
- Проверка корректности обработки ошибок и отображения сообщений пользователю.

## 2. Типы тестирования

- **Модульное тестирование серверной и клиентской части приложения**  
    Проверяются отдельные React-компоненты, страницы, вспомогательные функции, API-маршруты Express, middleware авторизации и серверные модули.
- **Функциональное тестирование интерфейса**  
    Проверяются основные функции приложения через пользовательский интерфейс: регистрация, вход, просмотр мероприятий, подача заявок, создание и редактирование мероприятий, работа с профилем, уведомления и административная панель.
- **Тестирование удобства использования**  
    Проверяется, насколько удобно пользователям разных ролей выполнять основные действия: найти мероприятие, подать заявку, создать мероприятие, обработать заявки, изменить профиль, воспользоваться админ-панелью.
- **Нагрузочное тестирование**  
    Проверяется стабильность серверной части при одновременных запросах к основным API: получение списка мероприятий, открытие мероприятия, авторизация, подача заявок, получение профиля и работа с уведомлениями.

## 3. Критерии начала и окончания тестирования

### Критерии начала тестирования

- Реализованы основные модули клиентской и серверной части приложения.
- Подготовлена структура базы данных PostgreSQL.
- Загружены тестовые данные: пользователи, профили, категории, мероприятия, заявки и уведомления.
- Настроено тестовое окружение для запуска frontend и backend.
- Установлены зависимости проекта.
- Подготовлены тестовые учётные записи для ролей: волонтёр, координатор и администратор.
- Настроены инструменты автоматизированного тестирования.

### Критерии окончания тестирования

- Все критические тесты выполнены успешно.
- Все блокирующие дефекты исправлены.
- Основные пользовательские сценарии проходят без ошибок.
- Проверены права доступа для всех ролей пользователей.
- Клиентская и серверная части проходят автоматизированные тесты.
- Интерфейс корректно отображается на основных разрешениях экрана.
- Нагрузочное тестирование не выявило критических сбоев в работе серверной части.
- Результаты тестирования зафиксированы в отчёте.

## 4. Ресурсы

### Инструменты

- **Vitest** - автоматизированное модульное тестирование клиентской и серверной части.
- **React Testing Library** - тестирование React-компонентов и пользовательского поведения.
- **jsdom** - эмуляция браузерного окружения при тестировании React-приложения.
- **Supertest** - тестирование API-маршрутов Express.
- **PostgreSQL** - тестовая база данных приложения.
- **npm scripts** - запуск тестов, покрытия, frontend и backend.
- **DevTools браузера** - ручная проверка интерфейса, адаптивности и сетевых запросов.
- **JMeter** - проведение нагрузочного тестирования API.

### Тестовые данные

- Тестовые пользователи с ролями: волонтёр, координатор, администратор.
- Тестовые профили пользователей.
- Тестовые мероприятия с разными датами, количеством мест, категориями и статусами.
- Тестовые заявки на участие в мероприятиях.
- Тестовые уведомления пользователей.
- Тестовые значения для проверки ошибок: неверный пароль, несуществующее мероприятие, недоступный профиль, отсутствующий токен авторизации, пользователь без нужной роли.

Проведённые функциональные тесты подтвердили корректную работу основных сценариев веб-приложения волонтёрской организации. Интерфейс корректно реагирует на действия пользователя, отображает результаты операций и не предоставляет недоступные функции пользователям без нужной роли.

# Нагрузочное тестирование в Apache JMeter

Нагрузочное тестирование проводилось с использованием инструмента Apache JMeter. Данный инструмент позволяет имитировать одновременную работу нескольких пользователей и выполнять серии HTTP-запросов к серверной части приложения. В рамках тестирования проверялась устойчивость API веб-приложения волонтёрской организации при массовом обращении к основным маршрутам [11]. 

Для каждого сценария в JMeter создавалась отдельная Thread Group, в которой задавались количество виртуальных пользователей, время разгона нагрузки и количество повторений. HTTP-запросы настраивались через элемент HTTP Request, заголовки авторизации - через HTTP Header Manager, а результаты фиксировались с помощью Summary Report, View Results Tree и Aggregate Report [14].

## Настройки JMeter, использованные при тестировании

|Элемент JMeter|Назначение|
|---|---|
|Test Plan|Общий контейнер для всех нагрузочных сценариев|
|Thread Group|Имитация одновременной работы пользователей|
|HTTP Request|Отправка запросов к API веб-приложения|
|HTTP Header Manager|Передача Content-Type и JWT-токена|
|JSON Extractor|Извлечение токена из ответа авторизации при необходимости|
|Constant Timer|Добавление небольшой задержки между запросами|
|View Results Tree|Просмотр отдельных запросов и ответов при отладке|
|Summary Report|Получение общей статистики по тесту|
|Aggregate Report|Анализ среднего времени ответа, медианы, percentiles и процента ошибок|

## Критерии успешного прохождения нагрузочных тестов

|Критерий|Ожидаемое значение|
|---|---|
|Ошибки 5xx|Отсутствуют|
|Ошибки 4xx|Допускаются только для ожидаемых отказов доступа|
|Среднее время ответа публичных GET-запросов|Не превышает допустимого значения для комфортной работы пользователя|
|Падение backend-процесса|Не допускается|
|Потеря соединения с БД|Не допускается|
|Нарушение лимита мест мероприятия|Не допускается|
|Создание дублирующих заявок|Не допускается|
|Некорректный доступ к админ-маршрутам|Не допускается|
