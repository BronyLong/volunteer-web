При небольшом количестве участников это работает, но при росте нагрузки появляются ошибки: заявки теряются, свободные места считаются вручную, а координатору сложно быстро понять, кто участвует и кто действительно пришел на мероприятие.

Поэтому задача проекта - собрать эти процессы в одной системе и автоматизировать ключевой сценарий: публикация мероприятия, подача заявки, обработка заявки, уведомление пользователя и фиксация участия.

**Текст выступления:**

Архитектура проекта разделена на три основные части.

Frontend на React отвечает за интерфейс и пользовательские сценарии.

Backend на Express отвечает за API, бизнес-логику, авторизацию, роли, заявки, уведомления и работу с персональными данными.

То есть приложение устроено как полноценная клиент-серверная система, а не как набор статичных страниц.

**Текст выступления:**

Самая важная бизнес-логика проекта - работа с заявками.

Заявка связывает волонтера и мероприятие. При ее создании сервер проверяет не только факт авторизации, но и роль пользователя, существование мероприятия, его актуальность, отсутствие дублирующей заявки и наличие свободных мест.

Именно этот блок показывает, что в проекте реализована не только форма отправки данных, а полноценная бизнес-логика.

## Слайд 7. Backend: безопасность и права доступа

**На слайде:**

Backend:

- JWT-авторизация;
- bcrypt для паролей;
- RBAC;
- серверные проверки;
- проверка владельца мероприятия;
- защита административных маршрутов.

(можно оставить просто текст)

**Текст выступления:**

На backend основной упор сделан на безопасность и контроль прав.

Для авторизации используется JWT. После входа пользователь получает токен, а защищенные маршруты проходят через middleware, который проверяет токен, пользователя и активность аккаунта.

Пароли не хранятся в открытом виде. При регистрации они хешируются через bcrypt, а при входе сравнивается не пароль, а его хэш.

Также реализована RBAC-модель - разграничение прав по ролям. В системе есть волонтер, координатор и администратор. Но главное - права проверяются не только на frontend. Даже если пользователь вручную отправит запрос к API, сервер проверит его роль.

Например, координатор не должен управлять чужими мероприятиями, а волонтер не должен иметь доступ к административным действиям. Такие проверки выполняются на сервере, потому что именно backend является главным уровнем защиты бизнес-логики.

## Слайд 8. Защита персональных данных и HTTPS

**На слайде:**

Защита данных:

- HTTPS при передаче;
- AES-256-GCM для персональных данных;
- HMAC для поиска email;
- ключи в переменных окружения;
- аудит без чувствительных данных.

(можно показать результат SELECT в БД и файл переменных окружения)

**Текст выступления:**

Отдельный инженерный блок - защита персональных данных.

При размещении приложения по доменному имени данные между пользователем и сервером передаются по HTTPS. Это защищает данные на этапе передачи.

Но защита не ограничивается одним HTTPS. Персональные данные в базе хранятся в зашифрованном виде. Для этого используется AES-256-GCM (один из самых современных и надежных алгоритмов симметричного шифрования данных, сочетающий шифрование AES с ключом 256 бит и режим аутентификации GCM (Galois/Counter Mode)). Шифруются email и поля профиля пользователя.

При этом возникает практическая проблема: если email зашифрован, его нельзя удобно искать обычным сравнением. Поэтому дополнительно используется HMAC-хэш (**HMAC** (Hash-based Message Authentication Code) - это криптографический код аутентификации, который использует секретный ключ в сочетании с хеш-функцией (например, SHA-256) для одновременной проверки **целостности** и **подлинности** сообщения) email. Он позволяет находить пользователя по email, не сохраняя сам email в открытом виде.

Ключи шифрования и секреты приложения хранятся не в базе данных, а в переменных окружения.

Поэтому при утечке одного только дампа базы злоумышленник не получает персональные данные в читаемом виде. Для расшифровки ему нужны ключи приложения. При этом корректно говорить, что утечка базы всё равно остается инцидентом безопасности, но реализованные меры существенно снижают ущерб.

В базе данных реализована не просто структура хранения, а дополнительный уровень защиты от некорректных данных.

Это важно, потому что корректность данных контролируется не только кодом приложения, но и самой базой данных.
